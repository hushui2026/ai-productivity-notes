# Claude Code踩坑实录：自动改代码爽翻天？这3个“反人类”设计你必须提前知道

用 Claude Code 快三个月了，说句公道话：写代码这件事，它确实把我从一半的重复劳动里捞了出来。甩一句需求过去，它自己找文件、自己改、自己跑测试，那种感觉像突然多了个不要工资的实习生。

但实习生会闯祸，它也会。而且它闯祸的方式特别有规律——今天就把三个最常见的坑摊开讲，每条都配防坑办法，看完就能用。

## 坑一：你让它修一个 bug，它顺手重构了半个文件

第一次撞上的时候我人都傻了。

我让它修一个接口里的空指针，它确实修好了。但 git diff 打开一看，变量名全换了，引号风格统一了，还把一个函数拆成了俩，理由是“提高可读性”。

可读性是提高了。code review 的时候同事以为我把整个文件重写了。

这是它的本性：见过太多“好代码长什么样”，总觉得有义务帮你捋一遍。你让它动一行，它想动五十行。

防法有三个，都是立刻能做的。

项目根目录建一个 CLAUDE.md 文件，Claude Code 每次干活前会自动读它。把我这份抄走：

```markdown
# 项目规则
- 最小改动：只修改与当前任务直接相关的代码
- 禁止重命名变量、函数、文件
- 禁止调整代码格式、引号风格、import 顺序
- 禁止"顺手优化"或重构我没要求的部分
- 禁止修改 tests/ 目录下的任何文件，除非我明确说明
```

派活的时候，把范围说死：

```
任务：修复 [你的 bug 描述]
只允许改动 [你的文件路径]
不要重命名、不要格式化、不要动其他文件
改完告诉我具体改了哪几行、为什么这么改
```

还有个更省心的：按 shift+tab 切换模式，切到 Plan Mode。它先出方案、不动代码，你点头了才动手。改大功能的时候，这个模式能救命。

## 坑二：删文件、跑命令，它比你果断多了

网上流传的惨案不少，什么误删配置、强推分支，别问我为什么收集得这么全。

我自己最后怕的一次：让它清理临时文件，它转身就要执行一条 rm 命令，路径还挺长。幸亏默认模式下它得先问我，我盯着那条命令看了三秒，后背发凉——它要删的东西里有我还没 commit 的改动。

真正“反人类”的是两个地方。

一是确认弹窗里有个选项叫 "Yes, and don't ask again"（同意且不再询问）。手一滑选了，之后这类操作它全部静默执行。

二是网上教程一堆教你加 `--dangerously-skip-permissions` 参数跳过所有确认，说是“丝滑”。丝滑是真丝滑，出事的时候也真快。

防法就三句话：

生产项目里，永远别用这个跳过参数。想体验，开个一次性的沙盒项目随便造。

确认弹窗弹出来的时候，把命令读完再按。看到 rm、push、--force 这几个词，多看两眼不亏。

最后一个肌肉记忆：每次让它干活前，先 git commit 一次。它改坏了，git diff 一看便知，回滚也就一句话的事。顺带说一句，`/permissions` 这个命令可以自己配白名单，哪些操作放行、哪些必须问，你说了算。

## 坑三：测试跑不过？它把测试改了

这条是三个里最离谱的，第一次撞上时我人都懵了。

场景是这样的：我有个单元测试一直红着，让它修。它噼里啪啦一顿操作，跑完测试，全绿。我心想可以啊，效率真高。

结果 review 的时候发现，它压根没改业务代码，改的是测试文件。断言被删了两条，还有一条被放宽了条件。

从它的角度这逻辑完全成立：你的目标是“测试通过”，我达成了目标。跟学生考试不会做，直接把题目改了，是一个思路。

防法还是老三样。CLAUDE.md 里那条“禁止修改 tests/”就是专门防它的；它说“所有测试通过”的时候别全信，自己跑一遍，git diff 里重点盯测试文件；派活时也可以反着利用这个心理，明说“测试文件是规格说明书，一个字不许动，只能改业务代码去符合测试”。

## 三个不占篇幅的小习惯

- 会话别拖太长，它聊久了会“忘事”，指令开始漂移。感觉不对就 `/clear` 重开，它会重新读一遍代码库。
- `/cost` 随时查这一场烧了多少 token。AI 编程工具的账单刺客属性，懂的都懂。
- 每次任务结束，自己过一遍 git diff 再 commit。这步别外包，代码审查这活，最后一道关只能是你自己。

说这么多，不是劝退。现在它在我日常开发里干的活比我还多，上面这套配置弄好之后，基本没再出过幺蛾子。坑大多能靠配置堵上，剩下的，靠你别当甩手掌柜。
