# 7 个 Claude Skills 模板实测三周：真香 3 个，看情况 3 个，删掉 1 个

Claude Skills 这东西，我是被逼着去了解的。以前每周一早上打开 Claude，第一件事是把上周干了什么、团队周报什么格式、老板不爱看长段这些背景，从头交代一遍。第三周我就烦了，跑去 GitHub 搜“怎么让 Claude 记住我的偏好”，翻到了 awesome-claude-skills 这个仓库，star 攒了一堆，里面全是别人写好的 Skill。

先把概念说人话。Skill 就是一个文件夹，核心是一个 SKILL.md 文件，写清楚这个技能什么时候触发、按什么流程干、输出成什么样，需要的话再塞几个参考文件进去。装好之后你说一句“跑周报”，它就知道该干嘛、什么格式，不用再从头教。说白了，就是把 Prompt 工程的成果打包成可复用的能力，相当于把你的工作流变成 AI 的肌肉记忆。

装法不麻烦。网页版 Claude 是 Settings → Capabilities → Skills，把文件夹打包成 zip 上传；用 Claude Code 的话，把文件夹丢进 ~/.claude/skills/ 就行。

仓库里东西挑花眼，我按“打工人每天真会用”的标准筛出 7 个，装上用了三周。丑话说在前面：真香 3 个，看情况 3 个，删掉 1 个。挨个讲。

## 周报生成：第一个让我觉得回不去的

它不是替你编周报，是把你那坨流水账按你团队的格式重新组装，顺手提炼。我一开始翻过车：它自己加戏，把我没提过的“跨团队协作”写成进展项，被领导当场问住。后来在模板里加了一句“只基于我提供的内容”，老实了。

```
---
name: weekly-report
description: 把用户提供的流水账整理成团队周报
---

流程：
1. 读取本周工作记录（可能很乱、口语化）
2. 按 [你的团队周报格式] 分组：项目进展 / 数据变化 / 风险与求助 / 下周计划
3. 每条动词开头，有数字写数字，不夸大
4. 只基于用户提供的内容，禁止推测或补充未提及的工作
5. 输出完附一行：对比常规事项，本周记录缺了什么（防漏报）
```

用的时候说“跑周报”，把流水账粘进去就行。那行“防漏报”是灵魂，比我自己人肉检查靠谱，我自己试下来每周这部分时间能省一半往上。

## 会议纪要：抠待办比人肉强，但有前提

转写稿丢进去，它吐三栏：已定事项（带负责人和截止时间）、未决议题、纯闲聊。翻车点很典型：中文里“下周再说吧”到底是定了还是没定，它一开始会搞错，我在模板里补了判定规则才稳。

```
---
name: meeting-todos
description: 从会议记录中提取待办清单
---

从转写文本提取：待办 / 负责人 / 截止时间 / 遗留争议。
规则：
- "回头看看""再说吧"不算待办，归入"未决议题"
- 没有明确负责人的，标"负责人缺失"，禁止默认填成会议主持人
- 输出三栏：已定事项 / 未决议题 / 闲聊（直接丢弃）
```

## 数据清洗：翻车最狠，教训也最值钱

这个本来能排第一。乱表、合并单元格、中英文混着的日期格式，它都能理顺，对我这种 Excel 半吊子算降维打击。直到有一次，它“好心”把空单元格按上下文补了数，我差点直接拿去做汇报。从那以后我模板第一行写死：缺失值只标注，不填充。这条是血泪换的，别问我具体损失了什么。

```
---
name: data-cleaning
description: 清洗表格数据
---

处理 [你的表格文件]：
1. 先只报告：行数、空值分布、异常格式，不动手
2. 经我确认后再清洗
3. 缺失值只标注，禁止按上下文推测填充
4. 每步改动列清单，可回滚
```

“先报告再动手”这条，说实话，所有 Skill 模板都值得抄。

## 竞品分析：做市场的装，其他人路过

结构是真稳，每次都是定位、定价、功能对比、差异化机会四块，不用重新搭框架。但它必须开联网搜索，纯靠模型自己回忆会编数据，还编得挺像。规则里那句“查不到就写数据缺失”是保命的。

```
---
name: competitor-report
description: 生成竞品分析报告
---

对比 [你的产品] 与 [竞品A] [竞品B] [竞品C]：
- 信息只用搜索结果，每条标出处
- 查不到的维度写"数据缺失"，禁止估算填充
- 结构：定位 / 定价 / 功能对比表 / 差异化机会（不超过 3 条）
```

## 代码 review：我半路出家用得浅，但看得出上限

拿同事的 Python 脚本测的，命名、边界条件、空值，点得挺细。它真正的价值在于能把团队规范喂进去，变成一个不摸鱼不嫌烦的 reviewer。全职开发的应该会真香，我这种偶尔写两行的不多做评价，讲真没有发言权。

```
---
name: code-review
description: 按团队规范审查代码
---

逐条检查：空值处理 / 边界条件 / 命名是否符合 [你的团队规范] / 重复代码
输出：位置 + 严重程度（阻塞或建议）+ 修改示例
不评价个人风格偏好，只报实质问题
```

## SEO 文章优化：降级当体检工具用

本来期望挺高，用下来一言难尽。它改完的文章有一股说不出的 AI 味，直接发出去读者是尝得出来的。我现在的用法是只让它出诊断——哪里关键词堆了、哪个标题弱、小标题利不利于扫读——改还是我自己动手。工具没变，用法降级，反而顺了。

```
---
name: seo-check
description: 诊断文章的 SEO 问题
---

检查 [你的文章]：
- 标题是否含核心关键词、有没有点击欲
- 关键词是否堆砌
- 小标题结构是否利于扫读
只出问题清单和修改建议，禁止直接改写全文
```

## 邮件分类回复：我最期待，也最先删

模板就不贴了，省得你手痒。问题不在于它写得差，挺礼貌的，就是不像我。每封回复都要改，改完的时间够我自己写两封。我一天十几封邮件的量，装它属于负优化；要是你每天邮件多到回不过来，倒可以试试，这种事看情况。

三周下来，我目录里留下的是周报、会议纪要、数据清洗。要是只许装一个，我推周报。不是别的不好，而是周报最高频、最重复、格式最死，恰好全是 Skill 的舒适区。

横评完最大的感受其实跟模板写法有关：这批东西好不好用，七分看里面那几条“禁止事项”。AI 翻车从来不是不会干，是太热心，总想多帮你一步。把“不许脑补”“不许填充”“先报告再动手”写死，成功率肉眼可见地上去。你自己写 Skill 的时候照这个思路来，八九不离十。

文末说好的“一键导入”：上面每段存成一个 SKILL.md（开头那几行 frontmatter 别删），各自放进独立的文件夹，打包 zip，在 Settings → Capabilities → Skills 里上传，齐活。
